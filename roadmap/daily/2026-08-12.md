## 今日目标

前两天已经把传感器流的 QoS 讲清楚了：`/robot/imu` 和 `/robot/joint_states` 是高频连续数据，优先新鲜度，所以用 `best_effort`。今天换到另一类通信：状态命令、故障事件和任务请求。

今天的重点是理解：为什么状态命令不能像传感器流一样“尽力而为”。对于 `/runtime/apply_event`、`/runtime/reset_fault`、`/runtime/query_status` 和 `/runtime/execute_task`，系统必须知道命令是否被接收、是否被拒绝、状态是否发生变化、最终结果是什么。

今天完成后，你要能讲清楚：

- 传感器流和控制命令的 QoS 判断标准为什么不同。
- Service 天然适合状态查询、复位和事件注入，因为它有 request / response。
- Action 适合长耗时任务，因为它有 goal、feedback、result 和 cancel。
- 状态机事件为什么必须返回 accepted / transitioned / previous_state / current_state。
- 面试里如何解释“可靠通信不是所有数据都 reliable，而是关键控制链路必须有确认”。

## 今日背景

当前 ROS2 Runtime Demo 里有三类控制语义：

```txt
Service:
  /runtime/query_status
  /runtime/reset_fault
  /runtime/apply_event

Action:
  /runtime/execute_task

State machine event:
  SensorTimeout -> ResetFault -> RecoveryDone
```

这些都不是“下一帧会覆盖上一帧”的数据。它们表示一次明确意图：查询、复位、注入状态事件、启动任务、取消任务。系统必须给出确定响应。

### 题目 2：整理控制命令语义表

写出下面这张表：

| 接口 | 类型 | 为什么需要可靠确认 | 验收证据 |
|------|------|--------------------|----------|
| `/runtime/query_status` | Service | 调用方要知道当前状态、错误码、恢复建议 | response 包含 `success=True` 和 `state=...` |
| `/runtime/reset_fault` | Service | 复位命令不能无声丢失 | response 包含 `runtime fault state cleared` |
| `/runtime/apply_event` | Service | 状态机事件必须知道是否被接受、是否转换 | response 包含 `accepted`、`transitioned`、`current_state` |
| `/runtime/execute_task` | Action | 长任务必须知道 goal 是否接受、是否完成或取消 | goal accepted、feedback、result、cancel result |

验收：每一行都能讲出“如果这条命令无声丢失，会造成什么工程后果”。

### 题目 3：验证 Service 可靠响应

在 ROS2 环境中启动 demo 后执行：

```bash
ros2 service call /runtime/query_status std_srvs/srv/Trigger "{}"
ros2 service call /runtime/reset_fault std_srvs/srv/Trigger "{}"
```

重点观察：

```txt
success=True
state=STANDBY
runtime_error=NONE
runtime_severity=INFO
runtime_recoverable=1
```

验收：能解释为什么 query/reset 不适合做成无确认 Topic。

### 题目 4：验证状态机事件可靠语义

执行故障恢复链：

```bash
ros2 service call /runtime/apply_event robot_runtime_demo/srv/ApplyRuntimeEvent "{event: SensorTimeout}"
ros2 service call /runtime/apply_event robot_runtime_demo/srv/ApplyRuntimeEvent "{event: ResetFault}"
ros2 service call /runtime/apply_event robot_runtime_demo/srv/ApplyRuntimeEvent "{event: RecoveryDone}"
```

重点观察：

```txt
accepted=True
transitioned=True
previous_state='STANDBY'
current_state='FAULT'
runtime_error='SENSOR_TIMEOUT'
```

验收：能说明 `accepted` 和 `transitioned` 的区别：

- `accepted=true`：事件名合法，系统理解这个请求。
- `transitioned=true`：事件在当前状态下真的触发了状态转换。

### 题目 5：验证未知事件拒绝

执行：

```bash
ros2 service call /runtime/apply_event robot_runtime_demo/srv/ApplyRuntimeEvent "{event: NoSuchEvent}"
```

预期：

```txt
accepted=False
message='unknown runtime event: NoSuchEvent'
```

验收：能解释为什么 reliable 不等于“所有请求都成功”，而是“请求必须有明确结果”。

### 题目 6：验证 Action 长任务可靠结果

执行：

```bash
ros2 action send_goal --feedback /runtime/execute_task robot_runtime_demo/action/ExecuteTask "{target_steps: 10}"
ros2 action send_goal /runtime/execute_task robot_runtime_demo/action/ExecuteTask "{target_steps: 0}"
ros2 run robot_runtime_demo action_cancel_test_client
```

重点观察：

```txt
Goal accepted
Feedback: current_step ...
Result: success: true message: task completed
Goal was rejected
cancel_result ... success=0 message="task canceled at step ..."
```

验收：能说明 Action 为什么比 Service 更适合长耗时任务：它能反馈进度，也能取消。

### 题目 7：准备 1 分钟面试表达

准备一段 1 分钟表达：

```md
在 ROS2 Runtime Demo 里，我把通信按数据语义分开设计。IMU 和关节状态是高频连续数据，最新样本更重要，所以适合 best effort；但状态查询、故障复位、状态机事件和任务 goal/result 是控制语义，必须有明确确认。比如 `/runtime/apply_event` 不只是发一个事件名，还要返回 accepted、transitioned、previous_state、current_state 和 runtime_error，这样调用方能知道命令是否被理解、状态是否真的变化。长耗时任务则用 Action，因为它能返回 goal 接受情况、feedback、result 和 cancel 结果。我的判断原则是：传感器流优先实时性，控制链路优先确定性，可靠通信的核心不是“所有消息都 reliable”，而是关键命令必须有可验证结果。
```

验收：能自然讲出来，重点放在“可靠确认”和“明确失败”。
