今天开始进入 DDS QoS 与通信可靠性。重点不是背参数名，而是把 QoS 和机器人系统里的真实通信场景对应起来：高频传感器数据、心跳、状态命令、故障事件、任务反馈，它们对“可靠、实时、历史缓存”的要求并不一样。

- `reliability` 解决“消息是否必须送达”的问题。

- `history` 和 `depth` 解决“队列保留多少历史消息”的问题。
- 为什么 `/robot/imu` 和 `/runtime/apply_event` 不应该使用同一套 QoS。
- QoS 选错时，系统可能出现阻塞、延迟堆积、状态丢失或误判超时。

## 练习题

### 题目 1：整理当前通信接口

先写出当前 demo 的通信清单：

| 接口 | 类型 | 数据特点 | 错误后果 |
|------|------|----------|----------|
| `/robot/imu` | Topic | 高频、连续、下一帧会覆盖上一帧 | 偶发丢帧可接受，阻塞不可接受 |
| `/robot/joint_states` | Topic | 高频、连续、用于状态观察 | 轻微丢帧可接受，长期缺失会触发故障 |
| `/runtime/heartbeat` | Topic | 低频、周期性、判断节点是否活着 | 连续丢失会导致 watchdog 误判 |
| `/runtime/apply_event` | Service | 离散控制事件，如 Fault / Reset | 丢失会导致状态机不同步 |
| `/runtime/execute_task` | Action | 长耗时任务，带 feedback / result | goal 和 result 必须可靠，feedback 可接受偶发丢失 |

验收：能说出每个接口最怕“丢消息”还是最怕“延迟堆积”。

### 题目 2：写 QoS 核心维度对比表

整理下面这张表：

| QoS 维度 | 常见取值 | 解决的问题 | 机器人例子 |
|----------|----------|------------|------------|
| `reliability` | `best_effort` / `reliable` | 是否要求消息可靠送达 | IMU 常用 best effort，控制事件应 reliable |
| `durability` | `volatile` / `transient_local` | 晚加入订阅者是否能收到历史消息 | 最新状态摘要可考虑 transient local |
| `history` | `keep_last` / `keep_all` | 保留最近 N 条还是全部历史 | 高频传感器通常 keep_last |
| `depth` | `1/5/10/...` | 队列深度，影响丢包和延迟 | depth 太大可能让旧传感器数据排队 |

验收：每一行都能举出当前 demo 里的接口例子。

### 题目 3：给当前 demo 做 QoS 选择

为下面接口写出建议配置和理由：

| 接口 | 建议 QoS | 理由 |
|------|----------|------|
| `/robot/imu` | `best_effort + keep_last(5) + volatile` | 高频连续数据，最新值更重要，不能为了补发旧帧阻塞系统 |
| `/robot/joint_states` | `best_effort 或 reliable + keep_last(5)` | 如果只是监控可 best effort，如果用于控制闭环要更可靠 |
| `/runtime/heartbeat` | `reliable + keep_last(3) + volatile` | 低频心跳不应轻易丢，保留少量最近记录即可 |
| `/runtime/apply_event` | Service 默认可靠语义 | 状态机事件必须明确成功或失败 |
| `/runtime/execute_task` | Action 默认可靠语义 | goal / result 可靠，feedback 关注最新进度 |

验收：不要只写参数，要写“为什么这个接口更怕什么风险”。

### 题目 4：分析 3 个故障场景

回答下面 3 个问题：

```md
1. 如果 `/robot/imu` 使用 reliable，并且订阅端处理变慢，会发生什么？
2. 如果 `/runtime/heartbeat` 使用 best effort，网络抖动时 watchdog 可能如何误判？
3. 如果 `depth` 设置很大，高频传感器数据的延迟会如何堆积？
```

参考答案方向：

- reliable 可能让发布端或中间队列为了补发旧数据付出额外等待，实时性变差。
- heartbeat 偶发丢失可能被 watchdog 当成节点失联，需要阈值和 QoS 一起设计。
- depth 太大时订阅端可能处理旧数据，看起来没有丢包，但控制使用的是过期状态。

验收：能把 QoS 问题说成工程后果，而不是参数解释。

### 题目 5：准备 1 分钟面试表达

准备一段 1 分钟表达：

```md
在 ROS2 里我不会把所有 Topic 都套同一套 QoS，而是按数据语义选择。比如 IMU 和关节状态是高频连续数据，最新值通常比每一帧都送达更重要，所以可以用 best effort、keep_last 和较小 depth，避免旧数据堆积影响实时性。心跳虽然也是 Topic，但它是 watchdog 判断节点存活的依据，低频且语义重要，因此更偏向 reliable，并用较小队列保留最近几次心跳。状态机事件、复位命令和 Action goal/result 属于离散控制语义，必须知道成功或失败，所以要用可靠通信。我的判断原则是：传感器流优先实时性，控制命令优先确定性，状态监控要在可靠性和误报之间做平衡。
```

验收：控制在 200 到 300 字，重点讲“按数据语义选 QoS”。
