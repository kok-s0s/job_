### 题目 4：新增 `/runtime/apply_event` Service

在 `runtime_node` 中新增 service：

```txt
/runtime/apply_event
```

行为要求：

- 收到未知事件时：`accepted=false`，不修改状态。
- 收到合法事件时：调用 `RuntimeStateMachine::process(event)`。
- 响应中返回 `previous_state`、`current_state`、`runtime_error`。
- `transitioned=true` 表示状态真的发生变化。
- 不能绕过状态机直接修改内部状态。

验收命令：

```bash
ros2 service list | grep /runtime/apply_event
ros2 service type /runtime/apply_event
ros2 service call /runtime/apply_event \
  robot_runtime_demo/srv/ApplyRuntimeEvent "{event: SensorTimeout}"
```

预期能看到类似：

```txt
accepted=True
transitioned=True
previous_state='STANDBY'
current_state='FAULT'
runtime_error='SENSOR_TIMEOUT'
```

### 题目 5：验证故障恢复链路

用 service 手动触发一条完整恢复链：

```bash
ros2 service call /runtime/apply_event \
  robot_runtime_demo/srv/ApplyRuntimeEvent "{event: SensorTimeout}"

ros2 service call /runtime/query_status std_srvs/srv/Trigger "{}"

ros2 service call /runtime/apply_event \
  robot_runtime_demo/srv/ApplyRuntimeEvent "{event: ResetFault}"

ros2 service call /runtime/apply_event \
  robot_runtime_demo/srv/ApplyRuntimeEvent "{event: RecoveryDone}"

ros2 service call /runtime/query_status std_srvs/srv/Trigger "{}"
```

验收标准：

- `SensorTimeout` 后进入 `FAULT`，错误码为 `SENSOR_TIMEOUT`。
- `ResetFault` 后进入 `RECOVERY`。
- `RecoveryDone` 后回到 `STANDBY`。
- 最终 `/runtime/query_status` 返回 `state=STANDBY runtime_error=NONE`。

## 常见错误

- 直接在 service 回调里把状态设成 `FAULT` 或 `STANDBY`，绕过 `RuntimeStateMachine::process()`。
- 忘记把 `srv/ApplyRuntimeEvent.srv` 加进 `rosidl_generate_interfaces()`。
- 改完接口后没有重新 `colcon build` 和 `source install/setup.bash`。
- service 响应只返回 success，没有返回前后状态，导致复盘时看不清转换过程。
- 未知事件返回成功，后续测试脚本会误以为状态机真的处理了这个事件。

## 面试表达模板

> 我不会让外部模块直接改机器人运行时状态，而是让它们通过 ROS2 service 发送事件。节点收到事件后只做解析和校验，真正的状态转换仍然由纯 C++ `RuntimeStateMachine` 统一处理。这样既保留了 ROS2 的可观测、可测试接口，又避免状态被多个回调随意篡改；调试脚本、监控 UI 和上层任务调度器都可以复用同一个入口。
