### 题目 3：手动验证 best effort 能收到传感器消息

启动 demo 后，在另一个 ROS2 终端执行：

```bash
ros2 topic echo /robot/imu --once --qos-reliability best_effort
ros2 topic echo /robot/joint_states --once --qos-reliability best_effort
```

预期能看到：

```txt
linear_acceleration:
  z: 9.8
```

以及：

```txt
name:
- joint_1
- joint_2
- joint_3
```

验收：能解释“这里不是为了证明不丢包，而是证明 best effort QoS 匹配时能正常收最新样本”。

### 题目 4：观察 QoS 不匹配现象

尝试用 reliable 订阅 best effort publisher：

```bash
timeout 5s ros2 topic echo /robot/imu --once --qos-reliability reliable
```

如果没有输出，说明 reliable subscriber 的请求高于 best effort publisher 能提供的可靠性，二者 QoS 不兼容。

验收：用自己的话写出一句结论：

```md
best effort publisher 只承诺尽力发送，不承诺重传；如果订阅端要求 reliable，就可能因为可靠性策略不兼容而无法匹配。
```

### 题目 5：用 topic info 验证 DDS 可见字段

执行：

```bash
ros2 topic info /robot/imu --verbose
ros2 topic info /robot/joint_states --verbose
```

重点观察：

```txt
Reliability: BEST_EFFORT
Durability: VOLATILE
```

注意：当前 ROS2 Jazzy / RMW 下，`History (Depth)` 可能显示为 `UNKNOWN`。这不代表代码没有设置 `KeepLast(5)`，只是 CLI 对该字段的展示有限；depth 仍通过节点 `[qos]` 日志和代码配置复盘。

验收：能区分“DDS introspection 能看到的字段”和“代码配置里确定存在的字段”。

### 题目 6：写 1 分钟实验结论

准备一段 1 分钟表达：

```md
我把 ROS2 Runtime Demo 里的 IMU 和关节状态 Topic 配成 best effort，是因为它们是高频连续传感器流，最新样本比补齐每一帧更重要。实验里我用 `ros2 topic echo --qos-reliability best_effort` 能正常收到数据，同时用 `topic info --verbose` 能看到 `Reliability: BEST_EFFORT` 和 `Durability: VOLATILE`。如果订阅端强行要求 reliable，就可能和 best effort publisher 不兼容，导致订阅不到消息。这个现象说明 QoS 不是越可靠越好，而是要按数据语义选：传感器流优先实时性，控制命令优先确定性，心跳则要兼顾可靠性和误报风险。
```

验收：能把实验现象、原因和工程选择讲在一起。
