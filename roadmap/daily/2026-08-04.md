## 今日背景

昨天我们已经让 `runtime_node` 输出统一结构化日志：

```txt
[runtime_log] ts=... node=runtime_node level=INFO event=heartbeat state=STANDBY runtime_error=NONE severity=INFO recoverable=1 latency_ms=... duration_ms=... message="runtime status ..."
```

但日志仍然偏向“给人和脚本看”。真正的 watchdog 更适合订阅一个稳定 Topic，例如：

```txt
/runtime/heartbeat
```

这个 Topic 的意义是：每个关键节点都周期性告诉系统“我还活着、当前状态是什么、最近一次工作是否正常”。

## 练习题

### 题目 1：区分日志、心跳、watchdog

用自己的话写出三者区别：

| 概念 | 主要用途 | 典型形式 |
|------|----------|----------|
| 日志 | 记录发生过什么，方便排障和复盘 | `[runtime_log] ...` |
| 心跳 | 周期性证明节点还活着 | `/runtime/heartbeat` Topic |
| watchdog | 订阅心跳并判断谁超时 | 3 秒无心跳触发 Fault |

验收：能解释“心跳不是一条普通日志，而是监控系统的输入信号”。

### 题目 2：设计心跳消息字段

先用 `std_msgs/msg/String` 承载 key-value 文本，后续再升级成自定义 msg。今天建议字段：

| 字段 | 示例 | 作用 |
|------|------|------|
| `node` | `runtime_node` | 心跳来源 |
| `seq` | `42` | 单节点递增序号 |
| `stamp_ms` | `1785835200123` | 发布时间 |
| `state` | `STANDBY` | 当前运行状态 |
| `runtime_error` | `NONE` | 当前错误码 |
| `severity` | `INFO` | 当前严重级别 |
| `recoverable` | `1` | 是否可恢复 |
| `status` | `OK/WARN/FAULT` | 给监控节点快速判断 |
| `message` | `runtime heartbeat` | 人类可读说明 |

验收：能说明为什么 `node`、`stamp_ms`、`seq` 是 watchdog 的核心字段。

### 题目 3：设计 3 个节点心跳来源

今天先按这 3 个节点设计：

| 节点 | 心跳内容 | 频率 |
|------|----------|------|
| `sensor_sim_node` | 传感器发布仍在运行 | 1Hz |
| `runtime_node` | 运行时状态机仍在运行 | 1Hz |
| `heartbeat_monitor_node` | 监控节点自身仍在运行 | 1Hz |

验收：写出每个节点一条样例心跳：

```txt
node=sensor_sim_node seq=1 stamp_ms=1785835200000 status=OK message="sensor publisher alive"
node=runtime_node seq=1 stamp_ms=1785835200001 state=STANDBY runtime_error=NONE severity=INFO recoverable=1 status=OK message="runtime heartbeat"
node=heartbeat_monitor_node seq=1 stamp_ms=1785835200002 status=OK message="heartbeat monitor alive"
```

### 题目 4：画出订阅关系

整理今天的目标结构：

```txt
sensor_sim_node --------\
runtime_node -----------+--> /runtime/heartbeat --> heartbeat_monitor_node
heartbeat_monitor_node -/
```

`heartbeat_monitor_node` 后续要维护一张表：

| node | last_seq | last_stamp_ms | age_ms | status |
|------|----------|---------------|--------|--------|
| `sensor_sim_node` | `42` | `...` | `800` | `OK` |
| `runtime_node` | `42` | `...` | `900` | `OK` |
| `heartbeat_monitor_node` | `42` | `...` | `0` | `OK` |

验收：能讲清楚“监控节点不关心业务细节，只关心每个节点最后一次心跳时间”。

### 题目 5：准备明天 watchdog 的判定规则

明天的 watchdog 可以先用这个规则：

```txt
if now_ms - last_stamp_ms > 3000:
    node_status = TIMEOUT
    runtime event = SensorTimeout
```

今天先写出 3 个边界情况：

1. 节点刚启动，还没有收到任何心跳：状态是 `UNKNOWN`，不要立刻 Fault。
2. 节点心跳延迟小于 3 秒：状态是 `OK`。
3. 节点心跳超过 3 秒：状态是 `TIMEOUT`，触发 Fault 或报警。

验收：能解释为什么 watchdog 需要“启动宽限期”，否则刚启动时会误报。

## 面试表达

可以这样讲：

```md
我把机器人运行时的可观测性分成三层：日志、心跳和 watchdog。日志用于复盘事件，心跳用于周期性证明节点还活着，watchdog 订阅心跳并在超时时触发故障处理。心跳适合用 ROS2 Topic，因为它是持续流式状态，不适合用 Service 被动查询。每条心跳至少包含 node、seq、stamp_ms、status 和 message，runtime 节点还会带 state、runtime_error、severity 和 recoverable。这样监控节点不需要理解每个业务节点的内部细节，只要维护最后一次心跳时间，就能判断节点是否超时。
```
