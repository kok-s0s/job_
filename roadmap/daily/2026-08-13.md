## 今日目标

前三天已经把 QoS 的核心判断跑通了：传感器流优先新鲜度，用 `best_effort`；控制命令优先确定性，用 Service / Action 返回明确结果。今天继续往下看 QoS 里另一个很容易被忽略的参数：`history + depth`。

今天的重点不是背 `keep_last(5)` 或 `keep_last(10)`，而是理解：当发布频率高于处理能力时，queue depth 会改变系统看到的是“最新数据”还是“排队积压的旧数据”。在机器人系统里，旧传感器数据有时比丢包更危险，因为它会让上层控制基于过期状态做决策。

## 今日背景

当前 ROS2 Runtime Demo 里，传感器流已经集中使用 QoS helper：

```txt
/robot/imu
/robot/joint_states
```

它们更关心最新状态，不应该让旧消息无限排队。今天要围绕这两个 Topic 做 queue depth 设计和验收。

建议你把 depth 先理解成一句话：

```txt
depth 是订阅端或发布端在来不及处理时最多保留多少条历史消息。
```

保留得太少，可能丢掉中间样本；保留得太多，可能让处理端追着旧数据跑，导致延迟不断增加。

### 题目 2：整理 queue depth 语义表

写出下面这张表：

| 场景 | depth 偏小的影响 | depth 偏大的影响 | 推荐判断 |
|------|------------------|------------------|----------|
| 高频 IMU | 中间样本可能被覆盖 | 旧 IMU 积压，处理延迟变大 | 优先最新值，depth 不宜太大 |
| JointState | 中间状态可能丢失 | 控制层看到过期关节状态 | 保留少量缓冲，关注 `latency_ms` |
| Heartbeat | 偶发调度抖动可能被放大 | 旧心跳可能掩盖节点已经超时 | depth 小且 reliable，结合 `age_ms` 判断 |
| 控制命令 | 不应通过 Topic 队列表达关键命令 | 积压命令可能按旧意图执行 | 用 Service / Action 明确确认 |

验收：能说出“depth 不是越大越安全”，它是在丢弃旧样本和积压旧样本之间做取舍。

### 题目 6：准备 1 分钟面试表达

准备一段 1 分钟表达：

```md
在 ROS2 Topic QoS 里，depth 不是越大越好。它决定 keep_last 策略下最多保留多少条历史消息。对于 IMU、JointState 这类高频传感器流，我更关心最新状态，所以会用较小 depth，让系统在处理不过来时丢弃旧样本，而不是把旧数据排队处理。如果 depth 太大，慢订阅者可能一直追着历史消息跑，表现为 latency_ms 持续变大；这对机器人控制很危险，因为上层拿到的是过期状态。我的判断原则是：传感器流用小队列保持新鲜度，心跳用小队列加可靠传输降低误报，控制命令不要依赖 Topic 队列，而是用 Service 或 Action 返回明确结果。
```

验收：能自然讲出来，重点放在“新鲜度、积压、延迟、取舍”。
